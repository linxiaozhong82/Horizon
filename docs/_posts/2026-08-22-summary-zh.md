## [开源 Qwen3-TTS 实现亚 50 毫秒语音响应延迟](https://nari-labs.com/blog/qwen3-tts-speed-cost-frontier/) ⭐️ 8.0/10

Nari Labs 对开源 Qwen3-TTS 模型进行优化，在单块 H100 上以每秒 10 个请求实现了 34ms 的 p95 首音频延迟（TTFA），将响应延迟降至 50ms 以内。他们还开源了实现代码、基准测试结果以及优化过程详解。 亚 50ms 的首音频延迟让开源文本转语音真正适用于实时语音助手，而生产级系统在这一延迟指标上往往表现不佳。这项工作表明开源模型能够与专有实时 API 竞争，有望降低构建响应式语音应用的门槛。 基准测试显示，在单块 NVIDIA H100 上、每秒 10 个请求时 p95 首音频延迟为 34ms，相关代码和基准已发布在 GitHub 上。文章还讨论了权衡取舍，指出其他开源方案在追求更低延迟时可能出现实时播放问题。

hackernews · toebee · 8月21日 15:51 · [社区讨论](https://news.ycombinator.com/item?id=49389952)

**背景**: 首音频延迟（TTFA）是指从发出文本转语音请求到音频开始播放之间的延迟，是实时语音应用的关键指标。Qwen3-TTS 是阿里巴巴 Qwen 团队开发的开源文本转语音模型系列，支持多语言和流式语音生成。vLLM-Omni、SGLang-Omni 等常见开源推理栈在生产环境中往往速度不够，这正是本次优化工作的动因。

Promptwatch 数据显示，ChatGPT 搜索中包含 site: 运算符的 fanout 查询比例从长期维持的 0.3%-0.5% 跃升至 2026 年 8 月 8 日的 16%-17%，与 OpenAI 的 GPT-5.6 Sol 更新相吻合。这标志着 ChatGPT 在搜索时针对特定域名进行定向检索的方式发生了显著变化。 这一变化表明 OpenAI 正在越来越多地引导 ChatGPT 搜索特定网站，从而改变了内容在 AI 生成回答中被引用的方式。对于新兴的生成引擎优化（GEO）领域来说，理解并针对域名级选择进行优化变得比以往更加重要。 该数据仅反映 Promptwatch 启用自动化跟踪的提示词，因此真实比例可能有所不同。Simon Willison 指出，OpenAI 刻意模糊系统提示词，其底层搜索工具可能更像是一个结构化的 search(query, recency, domains) 函数，而非直接输出 site: 运算符。

## [OpenAI 零数据保留的安全信号引发可审计性问题](https://www.reddit.com/r/OpenAI/comments/1vufo02/zero_data_retention_is_getting_crossinteraction/) ⭐️ 7.0/10

OpenAI 于 2026 年 8 月 19 日预览了 Private Safety Processing，使符合条件的 API 客户可以在不向 OpenAI 人员披露提示或响应内容的情况下，使用 Zero Data Retention 并检测跨交互滥用模式。当检测到风险时，客户会收到有限的安全信号。 这种架构可能通过解决隐私问题促进企业采用前沿模型，但缺少明确的审计机制可能会削弱信任。客户需要了解哪些策略被触发、评估了哪些交互窗口以及如何申诉误报。 OpenAI 表示，符合条件的客户可以使用客户控制的基础设施或客户持有的加密密钥，OpenAI 仅在检测到风险时收到有限的安全信号。然而，在无法读取提供商端内容的情况下进行执法会带来审计空白，因此客户需要公共信号模式、可复现的警报、独立审计或加密证明。

reddit · r/OpenAI · /u/Crescitaly · 8月21日 12:58

**背景**: 零数据保留（ZDR）是一种隐私保证，即 OpenAI 在处理后不存储提示或响应。Private Safety Processing 是一项新的预览功能，允许 OpenAI 在不向员工暴露内容的情况下检测跨相关交互的风险模式。由于提供商无法读取内容，它只能发送有限的安全信号，这引发了客户如何验证合规性以及对决定提出异议的问题。加密证明或公共模式可能有助于弥合这种信任差距。
